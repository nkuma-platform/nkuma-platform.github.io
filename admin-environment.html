Nkuma 環境を整備する

顧客 (または社内) の Nkuma 環境をゼロから開設します。標準は bicep による構築 (1.2) です。手動構築 (1.3) は同じ環境をポータルで 1 つずつ建てるための完全仕様 — 実際に手で建てる場面はまずありませんが、これを読めば「どのリソースが必要で、何をしているのか」が分かり、お客様のインフラ担当の方が環境の中身を確認する資料にもなります。

頻度: 顧客ごとに 1 回 ・ 月額資源が生まれる唯一の作業 (1 環境 ≈ ¥5,600〜5,700/月)
1.1 全体像 1.2 bicep で整備する (標準) 1.3 手動で整備する (完全仕様)

1.1 全体像 — これで何が建つのか

Nkuma 環境 = 顧客 1 つにつきリソースグループ 1 つ。中身は「共通基盤エンジン (データを預かる本体) + その周辺」の 10 リソースです。アプリ本体はここには含まれません — アプリは後から案件の CI が同じ環境に追加していきます (3 章)。

rg-nkuma-<customer>                     ← 器 (リソースグループ)
├── cae-nkuma-<customer>                Container Apps 環境 (エンジン・アプリ共通の実行場)
├── ca-nkuma-data-<customer>            共通基盤エンジン (データを預かる本体。外部非公開)
├── ca-nkuma-ops-<customer>             受付 (管理操作の取次窓口。普段は眠っている)
├── id-nkuma-ops-<customer>             受付の身元 (Managed Identity)
├── pg-nkuma-<customer>                 PostgreSQL (業務データの実体)
├── stnkuma<customer>                   Storage (添付ファイルの実体)
├── stnkuma<customer>token              Storage もう 1 つ (ログイントークン専用の金庫)
├── kv-nkuma-<customer>                 Key Vault (秘密の置き場)
└── crnkuma<customer>                   Container Registry (コンテナイメージ置き場)

これに加えて、Azure リソースではないものが 2 種類あります:

  • Entra ID のアプリ登録 3 本 (ログイン用 / エンジン用 / CI 用) — 認証の「名札」。テナント側に作る
  • ロール割り当て 3 種 — 「誰が何に触れるか」の配線。エンジンだけがデータ (PG / Storage) に触れる、という信頼境界をここで物理的に作る
設計の合言葉は「秘密ゼロ」: PostgreSQL はパスワード認証そのものを無効にし (= DB パスワードという秘密が存在しない)、Storage は共有キーを無効にする (= 鍵が存在しない)。接続はすべて Managed Identity (Azure が管理する身元)。唯一どうしても生まれる秘密 (ログイントークン金庫の SAS URL) だけを Key Vault に置きます。

1.2 bicep で整備する (標準ルート)

標準は IaC (foundation.bicep) による構築です。冪等 = 何度流しても安全で、初回の建設も、後日の設定変更・エンジン版更新も、すべて「記入用紙を変えて再実行」という同じ操作になります。

手順の流れ

  1. 権限の確認 — 実行者は対象 RG への Owner 相当 (ロール割り当て権限込み) が必要。純 Contributor では不可: リソースは建つのにロール割り当てで失敗する「半建ち」になります。無ければ建て始めずに情シスへ依頼 (「RG を作成し Owner を付与してほしい」)
  2. Entra アプリ登録 2 本を作る — ログイン用 app-nkuma-<customer> とエンジン用 app-nkuma-data-<customer> (作り方は 1.3 の該当節 と同じ。CI 用の 3 本目は 3 章のスクリプトが自動で作ります)
  3. 記入用紙を書く — params/foundation.bicepparam を顧客分コピーして記入 (下の表)
  4. 流す — az deployment group what-if で差分を確認 → 想定どおりなら az deployment group create
  5. PG ブートストラップ — pg-bootstrap.ps1 を 1 回実行 (エンジンの身元を DB の名簿に載せる。bicep では書けない領域)
  6. 完了確認 — バックアップ (PITR 7 日) と Blob のバージョニングが有効なこと

記入用紙 (bicepparam) の意味

bicep 本体 = 全顧客共通の設計図。bicepparam = その顧客の固有値を書く記入用紙で、顧客ごとに 1 枚持ちます。この紙は「その顧客環境の今あるべき姿」を表す台帳になり、後日の再実行 (名簿追加・版更新) もこの紙を書き換えて行います。

パラメータ必須何を書くか後で変える場面
customer✅顧客 slug (小文字英数ハイフン 3〜12 字)。全リソース名の種変えない (変える = 別環境)
environment—prod (既定) / testテスト面を建てる時だけ
location—リージョン (標準 = Japan East)変えない
pgEntraAdminObjectId / ...PrincipalName✅PostgreSQL の管理者 = 自分 (az ad signed-in-user show で取得)管理者交代時
pgEntraAdminPrincipalType—User (既定)ほぼ変えない
dataplaneImage—エンジンのイメージ (版込み)。初回は既定のプレースホルダのまま (下の約束事)一番よく変える欄① — エンジン版更新のたび (4 章)
dataplaneAppIdUri—エンジン用登録の api://<appId>登録作成後 1 回
kvOfficerObjectId—Key Vault に秘密を入れる人 (通常 = 自分)ほぼ変えない
opsOperatorOids—受付の運用者名簿 (objectId のカンマ区切り)。空 = 誰も通さない一番よく変える欄② — リポジトリ登録の顧客初回 (3 章)
opsLoginClientId—ログイン用登録の clientId (受付の認証用)。空 = 認証なしで建つお試し後、公開前に必須
覚え方: 最初に埋めるのは「顧客名 + 自分」だけ。イメージとログインの欄は建ててから育てる欄。

初回だけの約束事 (知らないと不安になる 3 点)

  1. 初回はプレースホルダイメージで建てる — エンジンイメージは自分の Container Registry から取得しますが、その取得権限 (AcrPull) は foundation 自身が配ります。鶏と卵になるので、初回は公開のプレースホルダで建てて権限を先に付け、イメージ取り込み後に dataplaneImage を実イメージへ変えて再実行します
  2. 初回リビジョンは「失敗」表示になります (仕様・実害なし) — プレースホルダは port 80 で待つのに受け口は 4100 を向いているため。実イメージへの差し替えで Healthy になります
  3. PG の身元登録だけは bicep で書けない — Managed Identity を DB ユーザー化する SQL は IaC の語彙の外。そのために pg-bootstrap.ps1 が別にあります (実行者の IP を一時許可 → 短命トークンで接続 → 名簿登録 + 権限付与 → 穴を閉じる。冪等)

再実行の型 — この後いつまた流すのか

場面記入用紙で変える欄
実エンジンへの切替 (初回直後)dataplaneImage
リポジトリ登録の顧客初回 (3 章)opsOperatorOids に CI の身元を追記
公開前opsLoginClientId
エンジン版更新 (4 章)dataplaneImage の版タグ
テスト面 (5 章)environment = 'test' (別 RG へ)
不安になったら what-if — 適用前に「何が変わるか」の差分が見えます。読んで想定どおりなら create。コマンドの正本は開発リポジトリの infra/README。

1.3 手動で整備する (完全仕様 — 理解と検証のために)

bicep が作っているものを、ポータル (または az CLI) で 1 つずつ建てる場合の仕様です。この順番どおりに作れば同じ環境が手で建ちます。各リソースの「なぜ」も添えてあるので、環境の中身を確認したいインフラ担当の方はこの節だけ読めば全体が分かります。

名前の <customer> は顧客 slug (例: nangok)。Storage / Container Registry は英数のみ (ハイフン除去)。リージョンは Japan East。

手順 0: リソースグループ

項目値
名前rg-nkuma-<customer>
タグ (以降の全リソース共通)nkuma-customer = <customer> / nkuma-environment = prod

手順 1: Entra ID アプリ登録 (2 本)

なぜ: 認証の「名札」。①は人がログインする時の入口 (全アプリ + 受付で共通 1 本 — アプリを増やしても登録は増やさず、戻り先 URL を追記するだけ)。②はエンジンへのアクセストークンの宛先名 (アプリの身元がエンジンに話しかける時、トークンの宛先 = audience としてこの名札を使う)。

登録表示名設定
① ログイン用app-nkuma-<customer>シングルテナント。シークレット・証明書は作らない (id_token 直接受領で成立するため不要)。サービスプリンシパルも作成しておく。リダイレクト URI は空で OK (アプリ登録時に追記されていく)
② エンジン用app-nkuma-data-<customer>シングルテナント。作成後、Application ID URI を api://<この登録の appId> に設定 (独自の URI 形式はテナント既定ポリシーに拒否されるため appId 形式)。サービスプリンシパルも作成

3 本目 (CI 用 app-nkuma-gha-<customer>) はリポジトリ登録の章で作ります (スクリプトが自動作成)。

手順 10: 受付 (Container App)

なぜ: エンジンは外部非公開なので、管理操作 (スキーマの宣言登録・初期 ADMIN 登録など) を外から届ける正規の窓口が要る。受付は同じエンジンイメージを「受付モード」で起動した小さな中継サーバで、ログイン + 運用者名簿で守られ、通った操作だけを自分の身元でエンジンに取り次ぐ。

項目値なぜ
名前ca-nkuma-ops-<customer> (実行場 = 手順 2 の環境)
身元user-assigned = 手順 8 の MIエンジンが「この身元しか受理しない」と照合する相手
受け口外部公開 (external 有効)、ポート 4100運用者がブラウザ / CLI で到達する (守りは認証 + 名簿)
イメージエンジンと同一 (取得身元 = 手順 8 の MI)配布物を増やさない
リソース / スケール0.25 vCPU / 0.5 GiB、min 0 / max 1使っていない間は眠る = 常設コストほぼゼロ
認証 (Easy Auth)Microsoft Entra、クライアント = ログイン用登録 (手順 1 の①)、未認証はログインへリダイレクト、許容 audience = <clientId> と api://<clientId>ログイン用登録を流用 (登録を増やさない)。公開前に必須 (お試し中は未設定でも建つ)

手順 11: ロール割り当て (3 種)

なぜ: 「誰が何に触れるか」の配線。データ系の権限をエンジンの身元だけに絞ることが、「アプリはエンジン経由でしか永続化できない」という信頼境界の物理的な実体です。

割り当て先ロールスコープなぜ
エンジンの MI (手順 9)AcrPullContainer Registry自分のイメージを取得する
エンジンの MI (手順 9)Storage Blob Data Contributor業務 Storage添付ファイルの読み書き。この権限を持つのは環境内でエンジンだけ
受付の MI (手順 8)AcrPull のみContainer Registry受付は中継するだけ — データ権限を持たせない
環境管理者 (人)Key Vault Secrets OfficerKey Vault秘密を投入できる人
アプリの身元に付くのは AcrPull + Key Vault Secrets User だけ (3 章で CI が付与)。PG / Storage の権限はアプリに一切付けません。

手順 12: PostgreSQL へのエンジン名簿登録 (ブートストラップ)

なぜ: エンジンが Managed Identity で PG に入るには、PG 側の名簿に「この身元はこのユーザー名」と登録が要る (Entra 管理者の SQL 操作。ポータルでは完結しない唯一の工程)。

  1. Entra 管理者 (手順 3 で自分を設定済み) として PG に接続 (短命トークン。実行者の IP を一時的にファイアウォールへ許可)
  2. pgaadauth_create_principal でエンジンの MI をユーザー ca-nkuma-data-<customer> として登録
  3. データベース nkuma への権限を GRANT
  4. 一時許可した IP を削除

標準ルートではこれを pg-bootstrap.ps1 が冪等に行います。

手順 13: 完成チェック

  • PG のバックアップ保持が 7 日 (PITR) になっている
  • 業務 Storage のバージョニング + 論理削除が有効
  • エンジンに実イメージを載せた後、リビジョンが Healthy
  • 受付に Easy Auth が構成されている (公開する場合)
