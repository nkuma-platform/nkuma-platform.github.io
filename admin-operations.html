ADMIN HANDBOOK — 5

困ったとき・その他の作業

定常章 (1〜4) に入らない、発生したときにやる作業をまとめています。

秘密の投入 破壊的マイグレーションの承認 ロールバック 非常口 テスト面 メンバーの環境トラブル

アプリに外部 API キー等の秘密が必要になったら

  1. アプリの身元 (Managed Identity) に Key Vault の読み取り (Secrets User) を付与する
  2. 値は人が自分の az セッションで Key Vault へ直接投入する — チャット・env ファイル・AI への貼り付けなど中間経路を通さない (AI に頼めるのはコマンドの組み立てまで。値を扱うのは人だけ)
  3. Container Apps の Key Vault 参照で環境変数に配線する (秘密の実体はアプリに配らない)

コマンドの正本は開発リポジトリの infra/README「秘密の置き場」。

破壊的マイグレーションで CI が止まったら

データが消えうるスキーマ変更 (列の削除など) を CI が検出すると、実行される SQL の計画を表示して停止します。これは事故ではなく、設計どおりの「人の判子待ち」です。

  1. Actions のサマリで計画 (何が消えるか) を読む
  2. 意図どおりなら、計画 ID (planId) を自分でタイプして承認ワークフロー (confirm-migration) を起動する — タイプさせるのは「読んだ」を担保する儀式です
  3. スキーマが古くなっていれば照合が不一致になり適用されません (安全側)
承認の記録は GitHub に残ります (誰がいつ confirm したか)。エンジン側の監査と合わせて、変更の三点 (変えた人 = git / 承認した人 = GitHub / 実行した身元 = CI) が追えます。

リリースを戻したいとき (ロールバック)

1 つ前の版のイメージへ差し戻します — 版は git タグ / Container Registry のタグ / 配備台帳 (registry.json) の 3 点に残っているので、迷子になりません。
戻し方は案件リポジトリ同梱のロールバック用ワークフロー (Actions → rollback を版名を入力して起動) の一本です — 手動の az containerapp update はイメージ名しか変わらず器の構成が揃わないため使いません。

受付が不通のとき (非常口)

管理操作の正規経路は受付 (1 章 手順 10) ですが、受付自体が動かない緊急時に限り、az containerapp exec でエンジンのコンテナへ直接入る非常口があります。

小さな緊急操作 (ADMIN 登録など) 限定 — コマンド長 (約 3KB) とレート制限があり、スキーマの宣言登録のような大きな操作には使えません。使ったら受付の復旧を先に。

テスト面を建てて壊す

常設のテスト環境は持ちません。
必要になったらテスト面用の記入用紙 (<顧客>.test.bicepparam — 記入用紙は環境ごとに 1 枚です) を用意して同じ IaC で別 RG に建て (構成差はスペックのみ、分離・鍵レス・認証の規律は本番と同一)、済んだら RG ごと削除します。
紙の environment も test にし、-Environment test を付けて実行してください (コマンドは 1 章の手順を参照。付け忘れると既存の公開面の紙が掴まれます)。

メンバーの環境が壊れたと言われたら

nkuma の配布物 (skill / 設定 / エンジン) は「入れ直せば直る」ように作られています。手で直そうとする前に、利用者ガイドの「困った時の手引き」へ誘導してください (update / 再実行で大半が解決します)。
