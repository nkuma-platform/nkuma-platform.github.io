ADMIN HANDBOOK — 3

Nkuma 環境にアプリを公開できるようにリポジトリを登録する

案件から「公開したい」と依頼が来たら行う受け入れの作業です。これが済むと、以降その案件は「main → deploy ブランチへのマージ」だけで公開まで自動で届くようになります — 作る人 (ドライバー) に Azure の権限は一切要りません。

頻度: 案件リポジトリごとに 1 回 ・ 権限: 対象 RG + Entra アプリ登録の所有
仕組み 手順 登録のあと

仕組み — 何を「登録」するのか

アプリの配備は、案件リポジトリに同梱された GitHub Actions が CI 用の身元 (app-nkuma-gha-<customer>) で全自動実行します。この CI 身元の認証は GitHub OIDC (フェデレーション認証) 限定 — つまり「この GitHub リポジトリの、このブランチの Actions である」こと自体が身分証明になり、シークレットも証明書も一切発行しません。

受け入れとは、この CI 身元に対して:

  • フェデレーション資格情報 (FIC) を追加して「この案件リポジトリを信じる」と教え、
  • 必要最小限のロール (RG の Contributor + 付与できるロールを 2 つに限定した条件付き RBAC Administrator) を付け、
  • アプリのログイン戻り先 URL と、エンジンへの宣言登録の通行証 (運用者名簿) を配線する

ことです。ほぼ全部スクリプトが冪等にやってくれます。

もう 1 つ、身元の話とは別に用意するものがあります — アプリ専用のログイントークン金庫です。公開されたアプリでは利用者が Entra ID でログインしますが (Easy Auth)、Container Apps は「ログインした人のトークンの預け先 (Blob) と、その鍵 (SAS URL)」を外から要求します (置き場を内蔵していない)。この鍵はこの環境で数少ない本物の秘密なので、CI には作らせず、管理者がアプリを迎えるこのタイミングで 1 回だけ用意して Key Vault に格納します。CI と アプリは Key Vault にある鍵を参照するだけです。

手順

入力: ドライバーからの依頼に リポジトリ名 / アプリ名 / 顧客名 / 初期 ADMIN にする人の UPN が含まれます (案件側のガイドが雛形を出します)。UPN は ① の -InitialAdminUpn にそのまま渡します。

  1. oidc-setup.ps1 を実行 — CI 用登録の作成 (初回のみ) + 案件リポジトリの FIC 追加 + ロール付与 + ログイン用登録への戻り先 URL 追記 + 初期 ADMIN の UPN 解決 (依頼の UPN を ID に引き当て、初回配備の CI が自動で ADMIN 登録できるようにする) + Variables 設定コマンド一式の出力、まで一括 (冪等)
  2. tokenstore-setup.ps1 を実行 — このアプリ用のログイントークン置き場づくり。Storage アカウントは増えません — 顧客共通のトークンストア用 Storage (1 章 手順 5 で作成済みの金庫室) の中に、このアプリ専用のコンテナ (部屋) easyauth-<アプリ名> を 1 つ切り、その部屋だけ開く鍵 (SAS、期限 1 年) を発行して Key Vault へ格納します (値は画面にもログにも表示されない。部屋を分けるのは、鍵が漏れても他アプリのトークンに届かないようにする分離)。これが無いと公開時のログイン構成が組めません。再実行すると SAS が上書きされる = 鍵のローテーションも同じスクリプト
  3. ① が出力した gh variable set コマンド一式をドライバーへ返信する — すべて非秘密の識別子です。実行は案件リポジトリに書き込めるドライバー側 (社内で同一アカウント運用なら管理者がそのまま実行しても OK)
  4. (顧客初回のみ) 運用者名簿に CI を載せる — 記入用紙 (1.2) の opsOperatorOids に ① が表示した CI 身元の objectId を追記して deploy-foundation.ps1 を再実行。これで CI がスキーマの宣言登録を行えるようになります
受付向け設定は自動化済み — ログイン用登録への「API の公開」3 点セット (宛先の正式名称 / 委任スコープ / Azure CLI の事前承認) は、oidc-setup が毎回冪等に確保します。順序を間違えると拒否される Graph 操作の罠ごと script が吸収しているので、手作業はありません。
Entra への書き込みは管理者側に残しています — CI に Graph 権限を渡すと権限も判子も増えるため、戻り先 URL の追記などはこの受け入れ作業のついでに管理者が済ませる設計です。コマンドの正本は開発リポジトリの infra/README「アプリの受け入れ」。

登録のあと — 管理者に残る仕事

  • 通常時: 何もしない。ドライバーの deploy マージごとに CI が「宣言登録 → ビルド → 差し替え → 版の記録」まで自動で行います
  • 初期 ADMIN も自動 — 手順 ① で UPN を渡していれば、初回の配備で CI がその人を ADMIN 登録します。管理者の配備後作業はありません (以降のロール変更はアプリの管理画面で完結)
  • 渡し忘れた / 後から依頼が来た場合だけ手動 — 管理者の道具箱 (infra) の 03_登録した生成アプリの初期ADMINを登録する/seed-admin.ps1 で登録します。初回の配備が通る前は実施できません (登録先の利用者名簿がまだ作られていないため — 順序は「deploy が通る → 登録できる」)
  • 破壊的マイグレーションの承認だけは人 — データが消えうるスキーマ変更を CI が検出すると、計画を表示して止まります。内容を確認し、計画 ID をタイプして承認ワークフローを起動した時だけ適用されます (5 章)
